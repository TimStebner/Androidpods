# ADR-0002: Project licensed under GPL-3.0-or-later

**Date**: 2026-08-13
**Status**: accepted
**Deciders**: Tim Stebner, Claude (development session)

## Context

`PROJECT.md` §25 anticipated a licensing decision without making one — the repository had no
`LICENSE` file. Implementing Apple's undocumented AAP protocol from scratch (§8.1 write
operations, packet field layouts) is substantial reverse-engineering work already done by
existing open-source projects: `kavishdevar/librepods` and `d4rken-org/capod`, both licensed
GPL-3.0. Adapting their protocol implementation would meaningfully shorten M2/M3 versus
independent reverse-engineering, but GPL-3.0 code cannot be copied into a differently-licensed
codebase without accepting its obligations (copyleft).

## Decision

License Androidpods under GPL-3.0-or-later (`LICENSE` at the repository root is authoritative).
This makes LibrePods and CAPod license-compatible sources: adaptation is permitted, subject to
per-file SPDX headers and attribution comments naming the upstream project/file/commit,
preserved upstream copyright notices, a project-wide `NOTICE.md` index, adapted code still being
reviewed against §11 layering and §30 coding standards rather than merged verbatim, and
distributing the resulting binary under GPL-3.0 with a written offer for source.

Protocol facts — PSM numbers, opcodes, packet field layouts, advertisement byte offsets — are
treated as factual interface information (not copyrightable expression) and remain usable
regardless of source, but every protocol constant still carries a comment naming the origin of
the observation (own capture vs. upstream documentation). First application: `AapPacketDecoder`
and `AapSession` (`core.airpods`), which adapt LibrePods' `Packets.kt`/`AACPManager.kt` field
layouts and handshake sequence with per-file attribution, verified against this project's own
real-hardware capture rather than trusted blindly.

## Alternatives Considered

### Permissive license (Apache-2.0 / MIT), reverse-engineer independently

- **Pros**: No copyleft obligations; broader downstream reuse.
- **Cons**: Cannot adapt LibrePods/CAPod's GPL-3.0 protocol work; the AAP handshake, packet
  layouts, and capability model would need independent discovery from raw captures alone.
- **Why not**: Would substantially slow M2/M3 for a solo/small-team project where the licensing
  cost (copyleft on distribution) is acceptable and the time cost of independent
  reverse-engineering is not.

### Permissive license, reference GPL-3.0 projects for understanding only (no adaptation)

- **Pros**: Keeps a permissive license.
- **Cons**: `PROJECT.md` §25 already requires "implementation provenance must remain clear" —
  reading GPL code and then writing "clean-room" equivalent logic is legally riskier than direct,
  attributed adaptation under a compatible license, and offers little practical benefit here since
  the protocol facts themselves (opcodes, offsets) are usable regardless of license.
- **Why not**: Attributed GPL-3.0 adaptation is both faster and legally cleaner than a
  fig-leaf clean-room reimplementation.

## Consequences

### Positive

- LibrePods/CAPod's AAP protocol research (handshake sequence, packet field layouts, capability
  data) becomes directly adaptable, cutting significant reverse-engineering time in M2/M3.
- Clear, enforceable attribution convention (SPDX header + per-file comment + `NOTICE.md`) keeps
  provenance auditable as the codebase grows.

### Negative

- Androidpods must be distributed under GPL-3.0, including a written offer for source — this
  forecloses a future closed-source or permissively-licensed distribution without relicensing
  (which would require agreement from any GPL-3.0-adapted-code contributors or removing that
  code).
- Any dependency or contribution must itself be GPL-3.0-compatible.

### Risks

- **Scope creep of "adaptation" into "copy"**: mitigated by §25's explicit rule to review adapted
  code against §11 layering/§30 coding standards rather than merge verbatim, and by keeping
  protocol facts (not copyrightable) separate from adapted implementation code (attributed).
- **Root-based features in upstream GPL-3.0 sources**: the VendorID-spoofing hook used by some
  GPL-3.0 reference implementations is root-based and is explicitly not adopted regardless of
  license compatibility — §8.4's root exclusion is independent of licensing.
